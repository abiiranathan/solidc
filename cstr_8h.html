Detailed Description

High-performance C string with Small String Optimization (SSO).

Key design decisions vs. the conventional implementation:

  1. Self-referential SSO pointer data always points to the live bytes — either into buf[] (inline) or a heap allocation. Every read/write goes through one pointer with zero branching; the "is-heap?" test is only needed for free/resize paths.
  2. Flat length and capacity in the struct root (uint32_t) No union-of-structs, no masked flag bits in length. The heap-flag lives in the MSB of capacity only. Reading length is always s->length.
  3. uint32_t sizes — 2 GB+ cap is plenty for a string type Halves the size of the length/capacity fields vs. size_t on 64-bit. Struct fits in 32 bytes (one half of a standard 64-byte cache line).
  4. Inline SSO buffer sized to fill the struct to exactly 32 bytes On 64-bit: ptr(8) + len(4) + cap(4) + buf(16) = 32 bytes. SSO holds strings up to 15 chars (+ NUL).
  5. SIMD-accelerated search with memchr first-byte scanning & guard bytes Avoids glibc's dynamic dispatch and internal strlen overhead for short needles.
  6. First-class String View (cstr_view) & Buffer-Length Interop Zero-copy views and explicit-length append/prepend/insert routines to avoid redundant strlen scans and handle non-NUL-terminated slices.

Struct layout (64-bit, little-endian): offset 0 : char* data (8 bytes) — always valid pointer offset 8 : uint32_t length (4 bytes) offset 12 : uint32_t capacity (4 bytes) — MSB = heap flag offset 16 : char buf[16] (16 bytes) — inline storage Total: 32 bytes

Warning
Do NOT shallow-copy cstr structs using assignment (cstr a = b;) or memcpy/realloc while in SSO mode; data points internally to buf within the same struct instance. Use cstr_copy() instead.

Typedef Documentation

◆ cstr

typedef struct cstr cstr

A dynamically resizable C string with SSO.

data is ALWAYS a valid, NUL-terminated pointer:

  • When heap flag is clear: data == &buf[0] (SSO path)
  • When heap flag is set: data points to malloc'd memory

This eliminates the branch in every read — callers just dereference data.
